## 2. Призначення та межі продукту

Вершина — персональний гейміфікований трекер руху до цілей. Допомагає обрати наступну дію, розділити велику задачу на посильні кроки, працювати сетами й бачити результат у прогресі, XP, іскрах, рівні, аурі та артефактах.

Принципи: винагорода за виконаний результат; тривалість таймера сама не дає балів; пауза не карається; користувачка керує своїм маршрутом. Символічний герой і аура — художня метафора.

| Уже є | Поки немає |
|---|---|
| Проєкти/місії, задачі, вкладені підкроки, серії лекцій | Спільна серверна база прогресу |
| Редагування, копіювання задач, перенесення, стрілки порядку | Автоматична синхронізація телефона й комп'ютера |
| Фокус «Взяти в роботу», таймер відкритої сторінки | Фонова служба таймера або push-нагадувань |
| Виконання, скасування, архів, кошик на 7 днів | Спільна робота, ролі всередині застосунку, модераторська панель |
| JSON-імпорт/експорт, локальні датовані копії | Необмежена історія кожної зміни прогресу |
| Світла/темна тема, адаптивна верстка, святкування | Вбудована модель ШІ, голосовий діалог, автоматичне виконання задач |

«Передати ChatGPT» формує текст, який треба скопіювати в чат. Кнопка сама не надсилає дані, не запускає агента й не гарантує виконання роботи. Реєстрація домену або перенос на GitHub не додають відсутніх функцій.

## 3. Інструкція користувачці

### Проєкт і маршрут

| Намір | Дія в інтерфейсі | Результат |
|---|---|---|
| Створити проєкт | Кнопка додавання місії біля вкладок → назва, бажаний результат, за потреби дата → Зберегти | Новий порожній проєкт |
| Змінити проєкт | Відкрити його вкладку → Редагувати | Змінюються його назва/мета/дата |
| Додати задачу | Додати крок → назва, результат, хвилини, XP | Невиконана задача |
| Подрібнити задачу | Підкрок біля потрібної задачі | Нова вкладена дія з часткою її бюджету |
| Створити курс | Створити серію → назва, кількість лекцій, шаблон `{n}`, дії по рядках, XP за лекцію, сет | Курс → лекції → дії, без негайного нарахування балів |
| Змінити задачу | Її «⋯» → Редагувати → Зберегти | Зберігається той самий елемент |
| Зробити копію | «⋯» → Копія → Зберегти | Нові ID; виконання та попереднє завершення не копіюються |
| Обрати наступну дію | Взяти в роботу | Гілка підіймається; фокус — на першій незавершеній кінцевій дії |
| Повернути автоматичний вибір | Повернути автовибір | Обирається перша доступна невиконана дія |
| Змінити порядок | ↑ або ↓ | Перестановка серед сусідніх елементів |
| Перенести | «⋯» → Перемістити → місце → підтвердження | Задача разом із підкроками та виконанням переходить в інше місце |
| Видалити задачу/підкрок | «⋯» → Видалити → підтвердити назву | Елемент і його нащадки у кошику на 7 днів |
| Видалити проєкт | Видалити проєкт → підтвердження | Увесь проєкт у кошику |
| Відкласти проєкт | В архів | Проєкт ховається з активних, XP зберігаються |
| Повернути проєкт | Архів → повернення в активні | Та сама структура й виконання |
| Відновити видалене | Кошик → Відновити | Повертається дерево, позиція й XP без подвоєння |

Якщо батьківський проєкт/задача теж видалені, спочатку відновити їх. Після 7 днів елемент не можна повернути звичайною кнопкою кошика; залишається перевіряти старий JSON. Очищення простроченого кошика відбувається під час роботи коду, не на сервері у фоні.

### Сет і вікна

Обрати наступний крок → за потреби тривалість → Почати сет. Таймер допомагає обмежити зусилля. Після фактичного результату натиснути «Крок виконано». Перезавантаження сторінки не відновлює активний відлік; мобільний браузер може призупиняти вкладку.

«Крок завеликий» відкриває додавання підкроку. «Налаштуватися на сет» дає вибір посильного сету. Це не ШІ-діагностика стану.

Меню «⋯» закривається тапом зовні або Escape. Усі діалоги застосунку закриваються тапом у порожній області поза вікном; незбережена форма не застосовується, а підтвердження видалення скасовується. Закриття не скасовує вже збережених дій. Натискання всередині діалогу не повинне його закривати.

## 4. Завершення, порядок і перенесення

Ці операції мають різний зміст і не повинні об'єднуватися під час доробок.

| Операція | Правило |
|---|---|
| Галочка кінцевого підкроку | Перемикає виконання; перераховує прогрес і XP |
| Усі підкроки виконані | Батьківська задача автоматично закреслюється/приглушується; залишається видимою |
| Галочка біля назви групи/лекції | Може завершити відразу всіх нащадків; зберігає один знімок їхніх позначок для скасування |
| Скасування галочки групи | Повертає позначки з `completionUndo`, перераховує XP і видаляє знімок |
| Старе завершення без знімка | Скасовує остаточну позначку, але не відтворює невідомий попередній стан дітей |
| Галочка проєкту | Доступна після виконання його задач; не виконує їх каскадно |
| Новий невиконаний підкрок | Реактивує батьків; не повинен залишати хибне повне завершення |
| Архів | Ховає проєкт; його XP лишаються у загальному підсумку |
| Кошик | Тимчасово прибирає елемент і його XP із підсумку; відновлення повертає їх |

Додаткова кнопка «Завершити задачу» в ряду команд скасована — не повертати її без нового доручення. Остаточна галочка лишається біля назви.

Виконані кінцеві дії показуються після невиконаних. Групи/проєкти переходять після активних за остаточним підтвердженням. Сортування показу не переписує ручний порядок вихідного масиву.

Знімок скасування — один список `{id, done, finalized}`, а не історія всіх натискань. Видалені чи перенесені вузли при скасуванні не створюються заново. Копіювання не переносить знімок виконання.

Перенесення працює на копії стану, перевіряє відсутність циклу та незмінність зароблених XP. Заборонене перенесення в себе/нащадка. Завершена кінцева дія не перетворюється на батьківську без скасування її виконання. Проєкт при перенесенні до іншого проєкту стає групою задач. Порожній проєкт наразі не переноситься.

## 5. XP, нагороди та герой

| Механіка | Реалізація |
|---|---|
| Початкова шкала | 25 XP — підтримувальна дія; 50 — звичайний результат; 100 — важливий; 200 — ключовий |
| Старі дії без явного XP | При нормалізації отримують 50 XP |
| Іскри | Сумарні XP / 5; можливі дробові значення |
| Рівень | `floor(XP / 200) + 1` |
| Шкала поточного рівня | `XP % 200` з 200 |
| Бюджет групи | Ділиться між її підкроками; бали заголовка не додаються поверх балів дітей |
| Частково виконана група | Бюджети розпочатих гілок фіксуються; решта ділить вільний залишок |
| Нуль XP новому підкроку | Можливий, коли доступний бюджет вичерпано; інтерфейс пояснює це |
| Зміна бюджету | У кореневої задачі, поки не виконана жодна її кінцева дія; для серії задається за лекцію |
| Перші артефакти | 50, 150, 350 XP |
| Подальші артефакти | 750 XP, потім кожні 400 XP |
| Відзнака курсу | За повне виконання; без додаткового XP за заголовок |
| Аура | Залежить від рівня й кількості нагород; не є додатковою валютою |

Тривалість сету не множить XP. Повторне виконання/скасування не повинне накопичувати нескінченні бали. Перерахунок при скасуванні, кошику або відновленні є нормальною поведінкою.

Святкування: конфеті за виконання дії; окрема сцена «Відсвяткувати» з SVG/CSS-персонажем приблизно на 4,6 секунди. Це не GIF. Підтримано `prefers-reduced-motion`; точний бажаний майбутній розмір героя не вважати реалізованим лише через історичне обговорення.

## 6. Прогрес, копії та відновлення

### Де лежить прогрес

Код — на GitHub. Опубліковані HTML/JS/іконки — на GitHub Pages. Особистий прогрес — `localStorage` браузера, ключ `summit-v1`. Серверної копії прогресу немає.

`localStorage` прив'язаний до **origin** (протокол, домен, порт), а не до облікового запису GitHub і не до шляху сторінки. `https://akara-center.github.io/vershyna/` та інші шляхи на `https://akara-center.github.io` мають спільний origin. У Вершині ключ поки загальний `summit-v1`; інший застосунок на цьому origin з таким самим ключем може з ним конфліктувати. Не змінювати ключ без міграції існуючого прогресу.

Інший браузер, профіль, пристрій або інший домен мають окремий стан. У приватному режимі дані можуть зникнути після закриття приватних вкладок. Дві одночасні вкладки Вершини не мають вбудованого узгодження конфліктів: уникати паралельного редагування одного прогресу.

Публічність коду не означає, що JSON-прогрес опублікований. Водночас локальне сховище не зашифроване паролем застосунку; доступ до профілю браузера дає доступ до його даних.

### Як зберегти й перенести

1. Дані → Зберегти JSON-файл. Назва містить дату/час у UTC.
2. Якщо завантаження не спрацювало: розкрити «Якщо файл не зберігається — скопіювати JSON», скопіювати повний текст та зберегти окремим `.json` у UTF-8.
3. Зберігати завантажений файл поза кешем браузера, наприклад у власній папці документів.
4. На іншій адресі/пристрої: Дані → обрати файл або вставити JSON → перевірити кількість місій/дій/виконаних → підтвердити заміну.
5. Перезавантажити сторінку, звірити задачі й XP. Після цього нові зміни вести в одному основному місці.

Імпорт **замінює**, а не об'єднує два прогреси. Перед ним створюється локальна копія поточного стану. Перевірка JSON не дорівнює його застосуванню: потрібне явне підтвердження. Пошкоджений або завеликий файл відхиляється; автоматично підміняти його стартовими даними не можна.

### Які копії створює застосунок

| Суфікс ключа після `summit-v1` | Зміст |
|---|---|
| `-before-github` | Одноразовий знімок перед переходом/оновленням |
| `-before-import` | Стан перед останнім імпортом |
| `-before-transfer` | Стан перед останнім перенесенням задачі/проєкту |
| `-before-project-change` | Перед останньою операцією архіву/кошика/повернення проєкту |
| `-before-v4`, `-before-ui-upgrade` | Історичні копії старих переходів; під час одноразового очищення прибираються |
| `<ключ копії>-created-at` | ISO-дата окремо від JSON |
| `-github-backup-reset-v1` | Маркер, що одноразове очищення старих копій уже виконано |

Підписи у «Дані» показують дату/час **за Києвом**, новіші копії — вище. Назви завантажуваних файлів мають UTC, тому година у назві може відрізнятися від підпису. Якщо дату старої копії не збережено, показується «дату створення не збережено»; вигадувати її не можна.

Одноразовий механізм: при старті з уже записаним валідним станом створити `-before-github` та дату → звірити їх → записати маркер → прибрати п'ять старих копій. При збої запису нової копії/дати/маркера старі копії зберігаються. Знімок надалі не перезаписується цим стартовим механізмом. Майбутні імпорти та інші операції знову можуть створювати свої копії — вимога «одна зараз» не є забороною майбутнього захисного збереження.

**Важливе уточнення:** на новому GitHub-origin одноразовий знімок технічно зберігає стан першого запуску з наявним `summit-v1`; якщо тоді список ще порожній, копія теж може бути порожньою. Назва «перед перенесенням» не доводить, що це особистий прогрес зі старої адреси. Для переходу використовувати власний експорт зі старої версії та звіряти огляд імпорту.

Ці копії — останні знімки за типами операцій, не необмежений журнал. Вони лежать у тому самому браузері й зникають при очищенні його даних. Окремого універсального менеджера видалення копій поки немає; не чистити `localStorage` вручну без збереженого JSON.

## 11. Формат даних

Поточна схема — **4**. Верхній рівень: `schemaVersion`, `theme`, `active`, `missions`, опційно `trash`. Реальний експорт може мати додаткові поля; не видаляти їх без аналізу сумісності.

| Об'єкт | Поля |
|---|---|
| Проєкт/місія | `id`, `name`, `goal`, `deadline`, `steps`; опційно `focusId`, `archived`, `finalized` |
| Крок | `id`, `name`, `result`, `minutes`, `done`, `xp`; опційно `children`, `kind: 'course'`, `collapsed`, `finalized`, `completionUndo` |
| Запис completionUndo | `id`, `done`, `finalized` для кожного збереженого нащадка |
| Запис trash | `id`, `kind`, `node`, `missionId`, `missionName`, `parentId`, `parentName`, `index`, `deletedAt` |

Синтетичний приклад, який можна давати іншій моделі:

```json
{"schemaVersion":4,"theme":"dark","active":"demo","missions":[{"id":"demo","name":"Приклад","goal":"Перевірка","deadline":"","steps":[{"id":"step-1","name":"Одна дія","result":"Результат","minutes":10,"done":false,"xp":50}]}]}
```

Основні обмеження валідатора: до 500 місій, 20 000 вузлів і глибини 8; непорожні унікальні ID; хвилини 1–120; XP — невід'ємне ціле; кореневий загальний бюджет до 1 000 000; бюджет дітей не перевищує бюджет батька. У schemaVersion 4 крок повинен мати XP; `children`, якщо задані, — непорожній масив. Майбутня схема понад 4 відхиляється. Серії в UI: 1–100 лекцій, 1–10 дій на лекцію; UI обмежує додавання підкроків суворіше за загальний валідатор. Імпорт файла — до 8 МБ; вставленого тексту — до 8 × 1024 × 1024 символів за перевіркою довжини.

`validate()` не є повною серверною валідацією всіх можливих полів, зокрема довільного стороннього trash. Для змін імпорту перевіряти його фактичну реалізацію, не обіцяти підтримку довільного JSON.

Ключові інваріанти: `earned(group)` сумує кінцеві дії; `isDone(group)` залежить від дітей; `finalized` не тотожне цьому підсумку; `ordered()` повертає порядок показу; `transfer()` зберігає загальний earned; `restoreTrash()` не дублює ID/XP.

## 12. Локальна робота у Windows

Для читання й запуску сайту не потрібні IDE або Node. Для розробки: Git, текстовий редактор; для тестів — Node 24, як у workflow. Нижче **пропонована** локальна папка; її наявність на комп'ютері власниці не перевірялася. Це окремий проєкт, не папка іншого сайту.

```powershell
New-Item -ItemType Directory -Force D:\Projects
Set-Location D:\Projects
git clone https://github.com/akara-center/vershyna.git
Set-Location D:\Projects\vershyna
git status
```

Якщо копія вже є, не клонувати поверх неї: перевірити `git status`, зберегти незакомічені зміни, тоді `git pull --ff-only`.

Локальний перегляд за наявності Python:

```powershell
py -m http.server 8000 --directory dist
```

Відкрити `http://localhost:8000/`. Якщо `py` недоступний, потрібен інший локальний статичний сервер, наприклад Live Server редактора. Відкриття index.html подвійним кліком через `file://` не є еквівалентною перевіркою збереження, secure-context API та шляхів GitHub Pages. Локальний прогрес на localhost також окремий від GitHub-origin.

## 13. Інструкція іншій моделі

### Як отримати доступ

Публічний URL дозволяє читати код через GitHub/браузер або завантажити ZIP. Для внесення змін потрібен підключений GitHub-інструмент, Git із авторизацією або доступ через авторизований вебінтерфейс. Наявність посилання не створює автоматично права запису. Не просити пароль чи токен у звичайному повідомленні чату.

Якщо є тільки читання: підготувати перевірений diff/гілку в доступному середовищі й прямо назвати відсутню можливість запису. Не називати локальну зміну опублікованою. Якщо інструмент не вміє налаштувати Pages чи створити репозиторій, можна використати дозволений авторизований інтерфейс GitHub; доступи не вигадувати.

### Порядок роботи

1. Прочитати `AGENTS.md`, `README.md`, цей паспорт, нове доручення й потрібний код. Останнє явне рішення власниці має перевагу над історією документа.
2. Перевірити `origin`, поточний `main`, останній commit, робоче дерево та останній успішний workflow. Не використовувати старий scratch або ZIP як актуальну базу без звірки.
3. Зафіксувати обсяг: візуальна правка, поведінка, дані або інфраструктура. Нові функції не випливають автоматично з прохання оновити паспорт.
4. Для ризикових змін зафіксувати базовий коміт і копію коду. Для міграцій — окремий JSON користувачки; перевірити сумісність і шлях відновлення до реалізації.
5. Створити робочу гілку, внести обмежену зміну; не включати сторонні файли, особистий прогрес, ключі або приватну документацію.
6. Виконати перевірки відповідно до зміни; нову поведінку перевірити на вкладеному синтетичному дереві. Наявні VM-тести не замінюють браузер.
7. Показати/перевірити результат до публікації. Якщо публікацію вже дозволено дорученням, не вимагати повторного погодження тієї самої дії; якщо погоджено лише прев'ю — не зливати в main.
8. Для публікації — commit → push/merge у main → дочекатися успішного workflow → перевірити саме live URL.

## 15. Публікація та відкат

### Звичайна публікація

Settings → Pages → Source: **GitHub Actions**. Workflow `.github/workflows/pages.yml` запускається на push у `main` і вручну через workflow_dispatch. Публікує лише папку `dist/`. Документи `docs/` видно в репозиторії, але вони не додають екранів у застосунок.

Послідовність CI: checkout → Node 24 → синтаксис → тести → configure Pages → завантаження артефакту dist → deploy. Права workflow: `contents: read`, `pages: write`, `id-token: write`. Секретів застосунку немає. Concurrency-група `pages`, автоматичне скасування попереднього запуску вимкнене.

Кожен push у main, включно з документацією, наразі запускає workflow. Наявність commit не означає успішного розгортання. У Actions перевірити потрібний SHA й зелений фінальний стан, потім живу сторінку. При червоному запуску відкрити невдалий крок і виправити причину. Не запускати нові однакові публікації лише тому, що попередня ще виконується.

Ручний повтор: Actions → Deploy GitHub Pages → Run workflow → main. Він публікує поточний обраний код; це не відновлення браузерного прогресу.

### Безпечний відкат коду

1. Зберегти поточний SHA, уточнити потрібний попередній SHA. Якщо змінювалися дані — зберегти актуальний JSON перед відкатом.
2. Перевірити підтримку поточних полів старим кодом. Однаковий schemaVersion не гарантує однакової поведінки `completionUndo`, кошика чи копій.
3. Відкотити потрібний коміт через **git revert** в окремій гілці, перевірити зміни, тести й синтетичний імпорт, тоді merge/push у main. Для merge-комітів потрібен окремий аналіз, не виконувати приклад механічно.
4. Дочекатися нового успішного workflow й перевірити live сайт. Не робити force-push або `reset --hard` поверх новішої спільної історії.

Приклад для одного звичайного коміту (підставити перевірений SHA):

```text
git switch main
git pull --ff-only
git switch -c fix/revert-change
git revert <BAD_COMMIT_SHA>
```

Далі тести, push гілки та pull request. Щоб просто переглянути стару версію локально без зміни публікації: окремий `git worktree add --detach <окрема-папка> <GOOD_SHA>` й локальний сервер. Не перемикати користувачку на старий JSON автоматично.

Повна копія коду: на GitHub **Code → Download ZIP**, або Git clone. Для збереження історії — Git bundle. ZIP коду не містить localStorage користувачки; експортувати прогрес треба окремо. Копія до переходу збережена приватно; старий Sites не є синхронним дзеркалом нового main.

## 16. Діагностика

| Симптом | Що перевіряти спочатку |
|---|---|
| Порожній список після відкриття нового URL | Це очікувано для нового браузера/origin. Імпортувати власний JSON, не заповнювати шаблоном |
| На телефоні й ПК різний прогрес | Автосинхронізації немає. Експорт/імпорт замінює стан; обрати головне місце роботи |
| Зник прогрес | Правильний URL, той самий браузер/профіль, не інкогніто; потім локальні копії/власний JSON. Не чистити браузер |
| Імпорт не приймається | Повний JSON без зайвого тексту, ліміти, schemaVersion, ID/XP, огляд помилки. Не видаляти поля навмання |
| Вибір файла не відкривається | Спробувати звичайний Chrome; резерв — вставити JSON текстом. Окремий браузер матиме окремий стан |
| Зміни не зберігаються | Повідомлення про сховище/квоту, дозволи браузера; спочатку експорт. При збої не закривати єдину вкладку з незбереженим результатом |
| Нова копія має стару назву або порожня | Дата, тип і огляд фактичного вмісту; назва не замінює перевірку даних |
| На GitHub новий код, на сайті старий | Actions для потрібного SHA, deploy, правильний URL, кеш. Не очищати site data |
| Сайт 404 | Pages Source, останній workflow, dist/index.html та правильний шлях /vershyna/ |
| Працює головна, не вантажиться JS/іконки | Відносні шляхи ./..., manifest, консоль/мережеві помилки |
| Мобільна верстка зламана | Усі пізні CSS-перевизначення, media queries, довгі назви/вкладеність, масштаб шрифту |
| Кошик не відновлює підкрок | Строк 7 днів, наявність батьківського проєкту/задачі, конфлікт ID |
| XP зменшилися | Скасування виконання або кошик; перевірити дерево. Архів сам не зменшує earned |

Історична проблема системного вибору JSON у переглядачі ChatGPT на Motorola остаточно не підтверджена як закрита. Перенесення на GitHub саме по собі не є доказом її виправлення. Старі втрати прогресу до появи кошика без копії не відновлені.
